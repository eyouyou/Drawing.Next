# 黑板接口收敛方案(设计稿)

> 状态:第一批(A1–A4)已实现。B1 已实现,最终方案与下文 §3 不同,以这里为准:
> - 作用域三个:`ReadScope()`(只读)、`UpdateScope()`(读后写,替代可升级读锁)、`WriteScope()`(写,合并了 `AcquireWriteLock` 与 `BeginTransaction`,结束时统一通知);共用一个返回类型 `BlackboardScope`。
> - `WriteIfChanged` 改名 `Write`,`ForceWrite` 不变。
> - 直接改名,不保留旧名、不标 `[Obsolete]`;趁 hevo.drawing 接业务前一次改完。
> - `AcquireWriteLock` 并进 `WriteScope` 后,原来"每写一次通知一次"变成"作用域结束通知一次"。改名前逐个查过框架里的写锁调用点,没有"写完马上在同一作用域里读派生值"的;要这么做的用 `UpdateScope` + 嵌套 `WriteScope`。
>
> 跟[手势接口方案](./手势接口方案.md)配套。
> 基线:`origin/main` 61ef76f,文中 `文件:行号` 都指这个提交。
> 两条硬约束:**不能变慢**(每项只接受"持平"或"更快");**锁模型不变**(`Read` / `Write` 裸读裸写,锁归外层作用域,`LowCode/DataBlackboard.cs:186-205`;00 号文档 `:83`)。

## 0. 结论

| 做不做 | 项 | 业务看得到吗 | 性能 |
|---|---|---|---|

| **第一批做** | A2 版本号字典从并发字典降成普通字典(先给锁外读的两处加读锁),两本不合并 | 看不到 | 更快 |
| **第一批做** | A3 `BeginTransaction` 不再每次分配对象 | 看不到 | 更快 |
| **第一批做** | A4 订阅、事件、版本号这些框架内部成员改 internal | 看不到(框架外没人用) | 持平 |

### 1.2 通知通道

黑板现在有三条通知通道,服务两个消费者:

| 通道 | 消费者 | 消费者要的其实是 |
|---|---|---|

### 1.3 性能问题

1. **每次提交都调用全部 Watch。** 黑板上**每一次**提交(十字光标每动一下鼠标就有一次)都把**所有** Watch 的提交回调调一遍,每个先进 `switchLock` 复查板(`FeatureExtensions.cs:259`,"修复 M5"),再进 `watchLock` 看标志(`:262`)。一张图大约 20 个 Watch(`Watch` / `WatchAsync` / `CombineLatest` 全仓 20 处调用),就是每次提交 40 次 monitor 进出。订阅用多播委托 `existing + callback`(`DataBlackboard.cs:157`),每次订阅分配新委托。
2. **版本号用并发字典。** `_portTokens` 和 `_identityTokens` 都是 `ConcurrentDictionary`(`:18`、`:45`),索引器写入内部要拿锁;违反 00 号文档"内部必须使用原生的 Dictionary,严禁使用 ConcurrentDictionary"(`Hevo.Charting/00.架构协议与开发规范.md:80`)。用并发字典的原因是有两处锁外读:`CombineLatest` 在 WatchAsync 的线程池回调里调 `GetVersion`(`FeatureExtensions.cs:306`),`Join` 的 `Where` 在管线释放锁之后才跑(`:340`)。
3. **退订要进写锁**(`:163-176`)。持读锁时退订会 `LockRecursionException`;管线销毁时先释放黑板再退 Watch 的顺序坑(`Hevo.Charting.Tests/ColumnReadScopeReleaseTests.cs:68` 标了"另行跟进")也从这里来。
4. (小)`BeginTransaction()` 每次 `new TransactionScope(this)`(`:324`),一次堆分配;同样拿写锁的 `AcquireWriteLock()` 返回 struct,零分配(`:70`、`:90`)。

## 2. 第一批:内部优化

### A1. Watch 收进黑板:按注册顺序的一张表 + 脏标志

替代 `Subscribe` / `Unsubscribe` / `OnTransactionCommitted` 三件套。

```csharp
// internal:只给 Watch 实现和联动镜像用。写锁内登记。
internal IDisposable AddWatch(object[] ports, Action<DataBlackboard> onCommit);

private sealed class WatchEntry
{
    public Action<DataBlackboard> OnCommit = null!;
    public bool Dirty;              // 只在写锁内改
    public volatile bool Removed;   // 退订置位,不拿锁
}

private readonly List<WatchEntry> _watches = new();                        // 注册顺序
private readonly Dictionary<object, WatchEntry[]> _watchersByPort = new();  // 写时复制,增删在写锁内重建
private int _dirtyCount;

private void NotifyPort(object port)                        // 现 :255-262
{
    if (_watchersByPort.TryGetValue(port, out var es))
        for (int i = 0; i < es.Length; i++)
            if (!es[i].Dirty) { es[i].Dirty = true; _dirtyCount++; }
    _observer?.OnPortWritten(port);                         // Schema 标脏 Feature,见 A4
}

private void Commit()                                       // 非事务写的末尾(现 :251)、EndTransaction 深度归零(现 :348)
{
    if (_dirtyCount == 0) return;
    for (int i = 0; i < _watches.Count; i++)
    {
        var e = _watches[i];
        if (!e.Dirty) continue;
        e.Dirty = false; _dirtyCount--;                     // 调用前清:抛异常也不会下次重跑
        if (!e.Removed) e.OnCommit(this);
    }
}
```

**为什么是扫表,不是待跑列表。** 现在的语义就是"每次提交按订阅顺序扫一遍所有处理器,只跑脏的",只是扫描要进两把锁、脏标志散在闭包里。换成一张表扫 bool,顺序、重入、异常三件事同时跟现状逐字等价,不用另外推理:

- **顺序**:按注册顺序执行。是否有 Watch 依赖这个顺序没逐个查(ViewportManager 钳 `ActiveRange` 和 ChartInteraction 刷十字光标都看视口端口,`Features/ChartInteractionFeature.cs:444`、`Features/ViewportManagerFeature.cs:104`),跟现在一致就不用查。
- **重入**:Watch 回调里再写黑板是常态(ViewportManager 的 Watch 写 `ActiveRange`,触发 ChartInteraction 的 Watch;同步 Watch 里写黑板的有 5 个文件)。回调里再写、再提交,就是嵌套再扫一遍表,脏的跑掉;外层接着扫,标志已清的跳过。深度优先,`ChartInteractionFeature.cs:866-877` 写 `UserRange` 后立刻读 `ActiveRange` 照旧读到新值。
- **异常**:标志在调用前清,抛异常的条目不会下次重跑;排在它后面的条目留到下次提交——跟现在一样(现在的脏标志也留到下次提交)。
- **O(N) 扫描不是问题**:每次提交扫约 20 个 bool,远比现在 40 次 monitor 进出便宜;`_dirtyCount == 0` 直接返回。等一张图上百个 Watch 再考虑待跑列表。
- 脏标志、`_dirtyCount`、两张表只在写锁内碰(写和提交都在写锁内,`DataBlackboard.cs:226-229`、`:328-356`),不需要另加锁。
- 一个 Watch 关心多个端口,一次提交里都写了,也只标一次脏、跑一次,跟现在"一次提交触发一次"相同。

**退订不拿锁。** `Dispose` 只置 `Removed`,下次写锁内 `AddWatch` 或 `Commit` 顺手把它从两张表里压缩掉。这同时解决 §1.3 第 3 条:持读锁时退订不再抛;已释放的黑板上退订也不碰锁,销毁顺序不再重要。并发窗口跟现在的 M5 一样——别的线程正在跑的那次提交可能还调一次,所以 `AttachWatchCore` 里 `currentBoard` 的复查保留(去掉 `watchLock`,只留切板用的 `switchLock`)。

**联动镜像也改用 `AddWatch`**。它现在挂的是"端口一写就回调"(`Linked/LinkedChartContext.cs:181`),回调里只记最新值、跨板写入放锁外(`:186-196`)。改成"提交时回调":非事务写入时两者是同一时刻;事务里从"逐个端口通知时"挪到"全部通知完之后",它读的是最新值、写在锁外,结果相同。加一条联动用例锁住。

**性能**:每次提交从"所有 Watch 各进两把锁"变成"扫 bool,只跑脏的";订阅不分配多播委托;`watchLock` 去掉;退订不进写锁。

### A2. 版本号字典降成普通字典,两本不合并

1. `GetVersion` / `GetIdentityVersion` 加 Debug 持锁断言,跟 `Read` 一样(`:195-198`)。
2. 锁外读的两处套读锁:`CombineLatest`(`FeatureExtensions.cs:302-309`)、`Join`(`:336-343`)。每次通知多进一次读锁,成本跟 Watch 回调里本来就要拿的锁一样。
3. `_portTokens`、`_identityTokens` 都换成普通 `Dictionary`,符合 00 号文档 `:80`。
4. `Dispose` 里的 `Clear`(`:386-387`)跟读者的时序靠已有的关门标志(`:13`、`:69-71`)保证,不另加东西。

**为什么不合并成一本**:实时 tick 原地改最后一根再 `ForceWrite` 只写 `_portTokens`(`:240`),`_identityTokens` 只在换缓冲时写(`:241`)。合并成一个结构体,最热路径要先读旧的 Identity 再写回,从 1 次查找变 2 次;.NET 5 没有 `GetValueRefOrAddDefault` 可以绕。

**性能**:稳态写入从一次并发字典索引器(内部拿锁)变成一次普通字典操作,更快。

### A3. `BeginTransaction` 不再每次分配

`TransactionScope` 的 `Dispose` 只是调 `EndTransaction()`(`:359-364`),没有自己的状态。每块黑板缓存一个实例反复返回即可,签名不变(仍返回 `IDisposable`)。

**性能**:每次事务少一次分配,更快。

**测试**:直接挂 `OnPortUpdated` / `OnTransactionCommitted` 数通知次数的用例(`Hevo.Charting.Tests/BlackboardTransactionTests.cs:28-30,57-58,83`)、直接调版本号的用例(`BlackboardIdentityVersionTests.cs`)、基准(`IncrementalCoreBenchmarks.cs:180`)改成用 internal 成员,这两个工程有 `InternalsVisibleTo`。

## 3. 迁移结束后:B1 新写法与作用域改名

hevo.drawing 迁移结束、不再频繁同步框架时,一次性改名并给旧名标 `[Obsolete]`,名字只换一次:

| 现在 | 改成 | 用途 |
|---|---|---|
| `WriteIfChanged(p, v)` | `Write(p, v)` | 裸写,跟现在一样不碰锁;只是改名,持平 |
| `ForceWrite(p, v)` | 不变 | 原名保留 |
| `AcquireReadLock()` | `ReadScope()` | 只读,连读几个端口要求同一时刻 |
| `AcquireUpgradeableReadLock()` + 嵌套 `AcquireWriteLock()` | `ReadScope(forUpdate: true)` + 嵌套 `Batch()` | 读完再写;内层结束就通知,外层后面接着读能读到 Watch 算出的派生值 |
| `AcquireWriteLock()` / `BeginTransaction()` | `Batch()`,返回 struct | 写;几个端口一起写时订阅者只看到一次 |

**`ForceWrite` 为什么不并进 `Write`**:跳过查脏只有 K 线最后一根原地改这类少数场景要,为它加一个 enum 和第三参数,让所有普通写入都背一个默认参数,不划算;`ForceWrite` 这个名字本身就说清了"跳过查脏",也跟 00 号文档、`AGENTS.md` 里"最后一根原地改再 `ForceWrite`"的说法一致,不用跟着改。

改名后业务的规矩:**只读用 `ReadScope`,要写用 `Batch`;`OnProject` 和手势回调里框架已经拿好了锁,直接读写。**

**注意**:`AcquireWriteLock` 是"每写一次通知一次",`Batch` 是"结束时通知一次"。在同一个作用域里写完一个端口又马上读它的派生值的框架调用点(如 `ChartInteractionFeature.cs:866-877` 写 `UserRange` 后读 `ActiveRange`),改名时不能一并换成一个大 Batch,要么保留嵌套的小 Batch,要么保留旧写法。逐个看,不一刀切。

## 5. 对手势方案的影响

- 手势 Watch 回调本来就在路由器的写锁里(同步 Watch 在写入当下执行,`DataBlackboard.cs:244-252`),直接 `board.WriteIfChanged(...)`;写多个端口套 `BeginTransaction()`(B1 后叫 `Batch()`),写锁可重入(`:24`)。
- 锁外执行(`OnCommitted` 这类业务回调)由 `WatchPointer` 的 `later(...)` 包装,黑板不新增公开接口。
- A1 让手势端口的分发更便宜:拖动中每次移动只跑监听手势端口的那几个 Watch,其余只是扫一个 bool。
- A1 退订不拿锁:手势 Feature 在回调里退订自己(例如一次性手势)也不会撞锁。

## 6. 测试

- **A1**:
  - 50 个 Watch 中只有 1 个关心被写的端口,断言只调用了 1 个。
  - 多个 Watch 同时脏时按注册顺序执行。
  - 回调里写端口触发另一个 Watch,且写完立刻能读到它算出的派生值(锁住深度优先语义)。
  - 回调抛异常后,下一次提交各 Watch 只跑一次。
  - 退订后不再调用,包括在别的 Watch 回调里被退订(替代 M5 的回归用例)。
  - 持读锁时退订不抛;已释放的黑板上退订不抛(`PipelineDisposeOrderTests.cs:55` 改成走 `AddWatch`)。
  - `Transact` 热插拔后 Watch 照常。
