# 黑板接口收敛方案(设计稿,待评审)

> 状态:**只是方案,没有改代码。** 跟[手势接口方案](./手势接口方案.md)配套:手势回调里要直接用黑板,黑板接口越少,写交互的人要记的规矩越少。
> 基线:`origin/main` 61ef76f,文中 `文件:行号` 都指这个提交。
> 硬约束:**不能变慢**。下面每一项都标了性能影响,只接受"持平"或"更快"。

## 0. 结论

业务看到的黑板从 14 个公开成员压到 **4 个**(外加 `IsDisposed`),分两类:

```csharp
// 作用域:决定"这段读写在哪把锁里"。锁由作用域一次拿住,读写本身不碰锁
using (board.ReadScope()) { … }               // 读
using (board.Batch()) { … }                   // 写(几个端口一起写,订阅者只看到一次、不会看到写了一半)

// 读写:裸读裸写,跟现在一样不加锁,只能在作用域里(或框架已经替你拿好锁的地方)调
board.Read(port);
board.Write(port, value);                     // 值没变就不写
board.Write(port, value, WriteMode.Always);   // 强制写(K 线最后一根原地改、手势序号)
```

**保持现在的锁模型不变**:`Read` / `Write` 依旧裸读裸写(`LowCode/DataBlackboard.cs:186-187` "极速裸读"、`:204-205` "把升级和加锁的权利还给外层"),锁由外层按作用域拿,一把锁罩住几个端口,读到的是同一时刻的值(00 号文档 `:83`)。收敛的是**作用域的种类和名字**,不是把锁塞进读写。

其余成员要么合并进上面这几个,要么改成框架内部(`internal`)。顺带拿到两处**提速**:Watch 通知只叫真正脏了的订阅者;两本版本号字典合成一本。

## 2. 收敛后的接口

### 2.1 读写:保持裸读裸写,只合并写法

**不加锁**。`Read` / `Write` 跟现在一样是裸读裸写,锁归外层作用域。理由:

- 一把锁罩住几个端口,读到的才是同一时刻的值;读写各自加锁只能保证单个端口不撕裂,跨端口照样撕裂(00 号文档"时空一致性",`:77`)。
- 自动加锁会诱导"读一个锁一次",一帧几十次进出锁,比外层一次拿住更慢。
- `OnProject` 外层已经有读锁(`Core/ReactiveSchema.cs:627`),手势 Watch 回调在路由器的写锁里(同步 Watch 在写入当下执行,`DataBlackboard.cs:244-252`),这两处本来就不需要业务碰锁。

只合并写法:

```csharp
public T Read<T>(DataPort<T> port);                                            // 不变
public void Write<T>(DataPort<T> port, T value, WriteMode mode = WriteMode.IfChanged);
public enum WriteMode { IfChanged, Always }
```

- `Write(port, v)` = 现在的 `WriteIfChanged`;`Write(port, v, WriteMode.Always)` = 现在的 `ForceWrite`。两个方法变一个,默认参数在编译期展开,`mode` 分支 JIT 后是一次常量比较,**性能持平**。
- `WriteIfChanged` / `ForceWrite` 保留为转发的旧名,加 `[EditorBrowsable(Never)]`。
- 锁外调用的检查保持现状:Debug 抛异常(`DataBlackboard.cs:190-199`、`:224-229`),Release 不检查(零开销)。只把异常信息改成指向作用域的写法:"先 `using (board.ReadScope())` / `using (board.Batch())`"。

### 2.2 四种锁合成三个作用域

| 现在 | 收敛后 | 说明 |
|---|---|---|
| `AcquireReadLock()` | `ReadScope()` | 连读几个端口要求同一时刻 |
| `AcquireUpgradeableReadLock()` | `ReadScope(forUpdate: true)` | 读完要写:里面先读,要写时再套一层 `Batch()`(可升级读锁里拿写锁就是升级,跟现在嵌套 `AcquireWriteLock` 等价) |
| `AcquireWriteLock()` | 公开的去掉,并入 `Batch()`;框架内部保留 internal 版 | 业务拿写锁只有一个目的——一次写几个端口 |
| `BeginTransaction()` | `Batch()` | 改名;`BeginTransaction` 留作转发 |

**为什么写锁可以并进 Batch**:两者都拿排他写锁(`DataBlackboard.cs:70` vs `:322`)。唯一区别是 Batch 把通知攒到结束时一次发(`:328-348`),对业务只会更好(订阅者不会看到写了一半)。

**性能**:Batch 比裸写锁多一次把端口放进脏集合(`_dirtyPorts`,预分配、零 GC),纳秒级;但多个端口时 Watch 只触发一次,而裸写锁是每写一次就通知一次,**整体持平或更快**。

**迁移风险**:有的框架代码在写锁里写完马上读"被 Watch 同步算出来的另一个端口"——比如写 `UserRange` 后读 ViewportManager 钳好的 `ActiveRange`(`Features/ChartInteractionFeature.cs:866-877`)。改成 Batch 后,通知要等 Batch 结束才发。所以框架内部保留 internal 的 `AcquireWriteLock`,只迁移明确安全的调用点,不一刀切。

### 2.3 订阅三件套合成一个内部 Watch 注册(更快)

**现在 Watch 是怎么实现的**(`WorkFlow/FeatureExtensions.cs:222-290`):每个 Watch 往它关心的每个端口挂一个"标脏"回调(`board.Subscribe`,`:266`),**同时**往黑板的 `OnTransactionCommitted` 挂一个"提交时看看自己脏没脏"的回调(`:267`)。于是:

- 黑板上**每一次**提交,都会把**所有** Watch 的提交回调调一遍。每个回调进一次 `lock (watchLock)` 看标志,没脏就返回(`:259-263`)。一张图几十个 Watch,十字光标每动一下鼠标就要提交一次。
- 订阅用多播委托 `existingAction + callback`(`DataBlackboard.cs:157`),每次订阅分配一个新委托。
- 退订和调用之间有竞态,靠 `switchLock` 二次检查兜底(`FeatureExtensions.cs:254-259` 的"修复 M5"注释)。

**收敛**:黑板自己管 Watch 条目和"待通知"列表。

```csharp
// internal:只给 Watch 实现用,替代 Subscribe / Unsubscribe / OnTransactionCommitted
internal IDisposable AddWatch(object[] ports, Action<DataBlackboard> onCommit);

private sealed class WatchEntry
{
    public Action<DataBlackboard> OnCommit = null!;
    public bool Pending;     // 本次提交里已经排进待通知列表
    public bool Disposed;    // 退订后置位;调用前检查,代替 M5 的 switchLock 二次检查
}

private readonly Dictionary<object, WatchEntry[]> _watchersByPort = new();   // 写时复制数组,增删 Watch 时重建
private readonly List<WatchEntry> _pendingWatches = new();                   // 跨提交复用,零 GC

private void NotifyPort(object port)
{
    if (_watchersByPort.TryGetValue(port, out var entries))
        for (int i = 0; i < entries.Length; i++)
            if (!entries[i].Pending) { entries[i].Pending = true; _pendingWatches.Add(entries[i]); }
    _observer?.OnPortWritten(port);     // Schema 判脏(见 2.4)
}

private void Commit()   // 非事务写的末尾(现 :251)、EndTransaction 的末尾(现 :348)
{
    for (int i = 0; i < _pendingWatches.Count; i++)   // 回调里再写会追加到列表尾部,同一循环里处理
    {
        var e = _pendingWatches[i];
        e.Pending = false;
        if (!e.Disposed) e.OnCommit(this);
    }
    _pendingWatches.Clear();
}
```

- 待通知列表只在写锁内碰(写和提交都在写锁内,`:226-229`、`:328-356`),不需要额外的锁。
- 一个 Watch 关心多个端口、一次提交里都写了,也只排一次,跟现在"一次提交触发一次"的语义相同。

**性能**:每次提交从"调用全部 Watch"变成"只调用脏了的 Watch",**更快**;订阅不再分配多播委托;`watchLock` 和 `switchLock` 两把锁不再需要。

### 2.4 `OnPortUpdated` 事件改成内部观察者

两个使用者:Schema 判脏(`Core/ReactiveSchema.cs:993-1006`)和 DevTools 内存雷达。改成一个 internal 接口,黑板持有一个(Schema)加一个可选的(DevTools):

```csharp
internal interface IBoardObserver { void OnPortWritten(object port); }
```

**性能**:多播事件调用改成接口调用,**持平或略快**。

### 2.5 两本版本号字典合成一本(更快)

现在每次写入要更新两本字典:`_portTokens`(普通 `Dictionary`)和列端口的 `_identityTokens`——后者是 **`ConcurrentDictionary`**(`DataBlackboard.cs:45`),违反 00 号文档自己的规定"内部必须使用原生的 Dictionary,严禁使用 ConcurrentDictionary"(`Hevo.Charting/00.Hevo.Charting 架构协议与开发规范.md:80`)。

合成一本:

```csharp
private struct PortVersion { public VersionToken Value; public VersionToken Identity; }
private readonly Dictionary<object, PortVersion> _versions = new();

internal VersionToken GetVersion(object port);          // 读 .Value
internal VersionToken GetIdentityVersion(object port);  // 读 .Identity
internal bool HasValue(object port);                    // 代替 WatchAsync / Join 里的 "GetVersion == default"(FeatureExtensions.cs:306,340)
```

两个版本号都改 internal。业务要"引用版本"走现有的 `FeatureContext.PortIdentity`(`Core/ChartFeature.cs:182-186`),不变。

**性能**:写入从两次字典操作(其中一次是并发字典)变成一次普通字典操作,**更快**。

**要确认的一点**:`ConcurrentDictionary` 当初可能是为了某个不持锁的读者。目前唯一的读者是 `PortIdentity`,在 `OnProject` 的读锁内;写入都在写锁内。实现时全仓搜一遍确认没有锁外读者。

## 3. 收敛后的样子

| 层 | 成员 |
|---|---|
| **业务(公开)** | `Read`、`Write`(含 `WriteMode`)、`Batch`、`ReadScope`、`IsDisposed` |
| **旧名转发(公开,隐藏)** | `WriteIfChanged`、`ForceWrite`、`BeginTransaction`、`AcquireReadLock`、`AcquireUpgradeableReadLock` |
| **框架内部(internal)** | `AcquireWriteLock`、`AddWatch`、`IBoardObserver`、`GetVersion`、`GetIdentityVersion`、`HasValue`、`PostAfterUnlock`、`DumpAllPortValues` |

业务要记的规矩从五条变成两条:**读写要在作用域里——读用 `ReadScope`,写用 `Batch`;`OnProject` 和手势回调里框架已经拿好了锁,直接读写。**锁的种类(读 / 写 / 可升级 / 事务)和 `WriteIfChanged` / `ForceWrite` 的区分不用再记。

## 4. 对手势方案的影响

- 手势 Watch 回调本来就在路由器的写锁里,直接 `board.Write(...)`;写多个端口套 `board.Batch()`(写锁可重入,`DataBlackboard.cs:24`)。上一轮提的 `PointerScope` 窄接口可以不要。
- 锁外执行(调用 `OnCommitted` 这类业务回调)用 `WatchPointer` 提供的 `later(...)`,黑板不新增公开接口,手势方案的 Q14 取消。
- **如果黑板收敛不做**,手势方案退回 `PointerScope` 方案,两者不互相阻塞。

## 5. 兼容

- 公开 API 只增不删:旧名全部保留并转发,旧代码不改也能编译、行为不变。
- 改成 internal 的那些,框架外没有使用者(§1.1)。hevo.drawing 同步框架时一起编译验证。
- 锁模型不变:`Read` / `Write` 仍是裸读裸写,锁外调用 Debug 抛、Release 不检查,跟现在一样。
- 行为变化只有一处:框架内部从 `AcquireWriteLock` 迁到 `Batch` 的调用点,通知从"每写一次发一次"变成"结束时发一次"(§2.2 的迁移风险)。
- .NET 5:全部是普通 C# 9 写法,没有新语言特性。

## 6. 测试

- **语义**:`Write` 默认等价 `WriteIfChanged`、`WriteMode.Always` 等价 `ForceWrite`;旧名转发后现有测试全过;`ReadScope(forUpdate: true)` 里套 `Batch` 能写;`Batch` 里写三个端口,Watch 只触发一次、且看到的是三个新值;Debug 下锁外读写的异常信息指向 `ReadScope` / `Batch`。
- **Watch 收敛**:
  - 50 个 Watch 中只有 1 个关心被写的端口,断言只调用了 1 个。
  - 回调里再写会触发下一个 Watch(同一次提交内)。
  - 退订后不再调用,包括在别的 Watch 回调里被退订的情况(替代 M5 的回归用例)。
  - `Transact` 热插拔后 Watch 照常。
- **版本号**:原地改最后一根后 `ForceWrite`,`Value` 版本变、`Identity` 版本不变(`CandleFeature` 现有用例全过)。
- **性能**(`Hevo.Charting.Benchmarks`,改前改后对比):
  - 50 个 Watch 的黑板上单次提交耗时(预期明显下降)。
  - 单次写入耗时(预期下降)。
  - 一帧 `ProjectAll` 耗时(预期持平)。
  - 十字光标拖动时每次鼠标移动的耗时(预期下降)。
- 全量测试 + `scripts/check-net5.ps1`。
