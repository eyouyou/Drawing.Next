### 1.2 性能问题

1. **每次提交都调用全部 Watch。** 每个同步 Watch 往关心的端口挂"标脏"回调(`board.Subscribe`,`FeatureExtensions.cs:266`),同时往 `OnTransactionCommitted` 挂"提交时看自己脏没脏"的回调(`:267`)。于是黑板上**每一次**提交(十字光标每动一下鼠标就有一次),都要把**所有** Watch 的提交回调调一遍,每个进一次 `lock (watchLock)` 看标志(`:259-263`)。订阅用多播委托 `existing + callback`(`DataBlackboard.cs:157`),每次订阅分配新委托;退订与调用之间的竞态靠 `switchLock` 二次检查兜底(`FeatureExtensions.cs:254-259` "修复 M5")。
2. **每次写入更新两本字典,其中一本是并发字典。** `_portTokens`(普通字典)和列端口的 `_identityTokens`(`ConcurrentDictionary`,`DataBlackboard.cs:45`,写入在 `:241`)。后者也违反 00 号文档"内部必须使用原生的 Dictionary,严禁使用 ConcurrentDictionary"(`Hevo.Charting/00.Hevo.Charting 架构协议与开发规范.md:80`)。
3. (小)`BeginTransaction()` 每次 `new TransactionScope(this)`(`DataBlackboard.cs:324`),一次堆分配;同样拿写锁的 `AcquireWriteLock()` 返回 struct,零分配(`:70`、`:90`)。

## 2. 第一批:内部优化 + 一个新写法

### A1. Watch 只通知脏了的订阅者,按注册顺序执行

黑板自己管 Watch 条目和"待通知"列表,替代 `Subscribe` / `Unsubscribe` / `OnTransactionCommitted` 三件套。

```csharp
// internal:只给 Watch 实现和联动镜像用
internal IDisposable AddWatch(object[] ports, Action<DataBlackboard> onCommit);

private sealed class WatchEntry
{
    public long Order;                  // 注册序号:提交时按它执行,保持现在"按订阅顺序"的语义
    public Action<DataBlackboard> OnCommit = null!;
    public bool Pending;                // 本次提交里已经排进待通知列表
    public bool Disposed;               // 退订后置位;调用前检查,代替 M5 的 switchLock 二次检查
}

private readonly Dictionary<object, WatchEntry[]> _watchersByPort = new();   // 写时复制数组,增删 Watch 时重建
private readonly List<WatchEntry> _pending = new();                          // 跨提交复用,零 GC

private void NotifyPort(object port)                        // 现 :255-262
{
    if (_watchersByPort.TryGetValue(port, out var entries))
        for (int i = 0; i < entries.Length; i++)
            if (!entries[i].Pending) { entries[i].Pending = true; _pending.Add(entries[i]); }
    _observer?.OnPortWritten(port);                         // Schema 判脏,见 A5
}

private void Commit()                                       // 非事务写的末尾(现 :251)、EndTransaction 末尾(现 :348)
{
    int done = 0;
    while (done < _pending.Count)
    {
        // 本轮新加进来的按注册序号排(通常只有一两个,插入排序),再逐个执行。
        // 回调里再写会追加到列表尾部,下一轮处理——跟现在"回调里写会再触发别的 Watch"同语义。
        SortByOrder(_pending, done);
        int end = _pending.Count;
        for (int i = done; i < end; i++)
        {
            var e = _pending[i];
            e.Pending = false;
            if (!e.Disposed) e.OnCommit(this);
        }
        done = end;
    }
    _pending.Clear();
}
```

- **为什么要按注册顺序**:现在提交回调挂在多播委托上,按订阅顺序执行。是否有 Watch 依赖这个顺序还没逐个查——例如 ViewportManager 钳 `ActiveRange` 和 `ChartInteractionFeature` 刷十字光标都看视口端口(`Features/ChartInteractionFeature.cs:444`)。按注册序号执行就跟现在一致,不用查。
- 待通知列表只在写锁内碰(写和提交都在写锁内,`DataBlackboard.cs:226-229`、`:328-356`),不需要另加锁。
- 一个 Watch 关心多个端口,一次提交里都写了,也只排一次,跟现在"一次提交触发一次"相同。
- **联动镜像也改用 `AddWatch`**。它现在挂的是"端口一写就回调"(`Linked/LinkedChartContext.cs:181`),回调里只记最新值、跨板写入放锁外(`:186-196`)。改成"提交时回调":非事务写入时两者是同一时刻;事务里从"逐个端口通知时"挪到"全部通知完之后",它读的是最新值、写在锁外,结果相同。加一条联动用例锁住。

**性能**:每次提交从"调用全部 Watch"变成"只调用脏了的",更快;订阅不再分配多播委托;`watchLock`、`switchLock` 两把锁去掉。

### A2. 两本版本号字典合成一本

```csharp
private struct PortVersion { public VersionToken Value; public VersionToken Identity; }
private readonly Dictionary<object, PortVersion> _versions = new();

internal PortVersion GetVersion(object port);   // 一次查找拿到 Value / Identity;HasValue = Value != default
```

`UsePort` 用 `.Value`,`PortIdentity` 用 `.Identity`,`WatchAsync` / `Join` 判"写过没"用 `.Value != default`。

**性能**:写入从"普通字典 + 并发字典"两次操作变成一次普通字典操作,更快。

**要先确认**:`ConcurrentDictionary` 当初可能是为了某个不持锁的访问。已知读者 `PortIdentity` 在 `OnProject` 读锁内,写入在写锁内;但 `Dispose` 里也有 `_identityTokens.Clear()`(`DataBlackboard.cs:387`),要确认它跟读者的时序。实现前全仓搜一遍。

### A3. `BeginTransaction` 不再每次分配

`TransactionScope` 的 `Dispose` 只是调 `EndTransaction()`(`:359-364`),没有自己的状态。每块黑板缓存一个实例反复返回即可,签名不变(仍返回 `IDisposable`)。

**性能**:每次事务少一次分配,更快。

### A4. `Write(port, value, mode)`

```csharp
public void Write<T>(DataPort<T> port, T value, WriteMode mode = WriteMode.IfChanged);  // 裸写,跟现在一样不碰锁
public enum WriteMode { IfChanged, Always }
```

- `Write(p, v)` = `WriteIfChanged`;`Write(p, v, WriteMode.Always)` = `ForceWrite`。
- 旧名保留公开、转发,加 `[EditorBrowsable(Never)]`,不标 `[Obsolete]`(B1 时再标)。
- 锁外调用的检查不变:Debug 抛(`:190-199`、`:224-229`),Release 不检查。只把报错信息改成指明该用哪个作用域。

**性能**:默认参数在编译期展开,`mode` 分支 JIT 后是一次常量比较,持平。

## 3. 迁移结束后:B1 作用域改名

hevo.drawing 迁移结束、不再频繁同步框架时,一次性改名并给旧名标 `[Obsolete]`:

| 现在 | 改成 | 用途 |
|---|---|---|
| `AcquireReadLock()` | `ReadScope()` | 只读,连读几个端口要求同一时刻 |
| `AcquireUpgradeableReadLock()` + 嵌套 `AcquireWriteLock()` | `ReadScope(forUpdate: true)` + 嵌套 `Batch()` | 读完再写;内层结束就通知,外层后面接着读能读到 Watch 算出的派生值 |
| `AcquireWriteLock()` / `BeginTransaction()` | `Batch()`,返回 struct | 写;几个端口一起写时订阅者只看到一次 |

改名后业务的规矩:**只读用 `ReadScope`,要写用 `Batch`;`OnProject` 和手势回调里框架已经拿好了锁,直接读写。**

**注意**:`AcquireWriteLock` 是"每写一次通知一次",`Batch` 是"结束时通知一次"。在同一个作用域里写完一个端口又马上读它的派生值的框架调用点(如 `Features/ChartInteractionFeature.cs:866-877` 写 `UserRange` 后读 `ActiveRange`),改名时不能一并换成一个大 Batch,要么保留嵌套的小 Batch,要么保留旧写法。逐个看,不一刀切。

## 5. 对手势方案的影响

- 手势 Watch 回调本来就在路由器的写锁里(同步 Watch 在写入当下执行,`DataBlackboard.cs:244-252`),直接 `board.Write(...)`;写多个端口套 `BeginTransaction()`(B1 后叫 `Batch()`),写锁可重入(`:24`)。
- 锁外执行(`OnCommitted` 这类业务回调)由 `WatchPointer` 的 `later(...)` 包装,黑板不新增公开接口。
- A1 让手势端口的分发更便宜:拖动中每次移动只调用监听手势端口的那几个 Watch,不再把全部 Watch 都过一遍。

## 6. 测试

- **A1**:
  - 50 个 Watch 中只有 1 个关心被写的端口,断言只调用了 1 个。
  - 多个 Watch 同时脏时按注册顺序执行。
  - 回调里再写会触发别的 Watch(同一次提交内)。
  - 退订后不再调用,包括在别的 Watch 回调里被退订(替代 M5 的回归用例)。
  - `Transact` 热插拔后 Watch 照常。
  - 联动:主图事务里连写视口三个端口,副图收到最终值。
- **A2**:原地改最后一根后 `ForceWrite`,`Value` 变、`Identity` 不变(现有 `BlackboardIdentityVersionTests` 全过)。
- **A3**:`BeginTransaction` 连开 1000 次零分配;嵌套事务照常。
- **A4**:`Write` 默认等价 `WriteIfChanged`,`WriteMode.Always` 等价 `ForceWrite`。
- **全量**:现有测试全过 + `scripts/check-net5.ps1`。
- **性能**(`Hevo.Charting.Benchmarks`,改前改后对比):
  - 50 个 Watch 的黑板上单次提交耗时(预期明显下降)。
  - 单次写入耗时(预期下降)。
  - 一帧 `ProjectAll`(预期持平)。
  - 十字光标每次鼠标移动(预期下降)。
