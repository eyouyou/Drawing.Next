# Hevo.Charting 接口与心智模型评审(2026-10)

姊妹篇:[架构评审-2026-10.md](./架构评审-2026-10.md)(查正确性:bug、死锁、泄漏)。本篇查**好不好用**:
概念数、概念重叠、命名一致性、"最直观的写法是不是正确的写法"、编译通过却静默出错的陷阱、迫使业务绕路的能力缺口,以及文档和代码讲的是不是同一个模型。
另附 FuturesPC(FinNex)迁移适配分析。

- **基准**:业务仓库 hevo.drawing `c116bbe`。框架等同上游 `505b97a`,含最新 Hook 接口;另外带着真实的业务调用方:Hevo.Drawing、MultiStockDemo、LowCodeDemo、Hevo.Core、Hevo.Trade.*。
- **方法**:分 5 个切面(Feature 编写、Layer 与渲染、屏幕装配、数据与计算、文档 / 低代码 / Python),每个切面只看文档和公开 API,推演 3 个真实任务,再去看业务代码实际怎么写的。另做一份 FuturesPC 功能盘点,和本库逐项对照。每个切面人工抽查 1–2 条,标 ✅ 的已对照代码核实。
- **全部是静态阅读**,没有编译,也没有运行。

## 总结论

**核心模型是对的,值得保留**:
- 黑板 → 端口 → Feature 在 `OnProject` 里用三种 Use → Trait → Layer 录指令 → 渲染器统一做像素规则。
- 四段 builder 加 `DefineDataFlow` / `DefineFeatures` 两段式结构,读起来就是页面结构。
- 缓冲按纪元回收、WatchAsync 合并通知、两种版本令牌,这些底层机制扎实。
- DocSamples 随测试编译,是全仓库最可靠的文档。

**但接口还没准备好大规模迁移。** 五个切面独立得出了同一个结论,问题不在概念数多,而在三件事:

1. **静默失效太多。** 很多写法看着能跑,其实不对,而且不报错:
   - 联动时 hit 端口用错,十字光标就不联动。
   - 忘了 Seed 比例尺,黑屏。
   - AutoScale 漏列端口,线被裁掉。
   - 图层挂上了却一帧不画。
   - 蓝图拼错键名,图是空白的。
   - Python handler 漏写 signature,直接被跳过。
2. **迁移最常用的高层能力,框架没提供,业务只能各写各的,而且已经走样**:
   - 切合约 / 切周期
   - 实时更新最后一根
   - 历史分页
   - 按 key 替换 Feature
   - 多输出指标
   - 填充绘制
   - 坐标 helper
3. **文档过期**:01 号文档的标准范例编译不过;同一条规则散在多份文档里,说法不一;术语一词多义。

迁移方式:FuturesPC(FinNex)是 Avalonia 12 / .NET 8 应用(✅ 已核实),它的图表功能要按本库的模型在 WPF 上重写;UI 代码不能直接搬,与 UI 无关的部分(公式引擎、纯计算、旧数据格式)可以复用。见文末"迁移适配"。

### 框架冻结下的做法

前提:**迁移期间不碰框架**(`Hevo.Charting*` 目录),迁移只改业务代码。所以要把上面的门槛分成两类:

**A. 迁移开始前,必须先在框架里做完,然后冻结**

| 事项 | 为什么业务层绕不过去 |
|---|---|
| 架构评审的 P0 / P1 修复(三个修复会话正在做),修完后同步到 hevo.drawing | 死锁、请求悬空、Composite 黑屏、Transact 清理不全,这些都在框架内部,业务代码改不到 |
| G5 RequestBus 分道 | 同上;已包含在第一批修复里 |
| G9 中的 `UpdateData`(删掉或修好) | 公开 API 本身是错的。业务层的办法只能是"约定不用它",这条可以降级到 B,但最好冻结前顺手修掉 |

冻结点:三批修复合并、同步到 hevo.drawing 后,打一个标签,迁移从这个标签开始。

**B. 业务层用公开 API 自己做,集中放在一个业务侧的"迁移支撑层"**

建议在 hevo.drawing 里新建一个工程(例如 `Hevo.Drawing.Foundation`),专门放这些,所有迁移屏幕都基于它:

| 门槛 | 业务层做法 | 可行性 |
|---|---|---|
| G1 hit 端口 / 比例尺 / 视口默认值 | 业务 Schema 基类:统一传 `HitPort`、默认 Seed 比例尺、显式写视口参数 | 可行 |
| G2 切合约 / 切周期 | 业务数据源基类自己记录"这次是切换还是刷新",对外提供 `SwitchAsync` | 可行 |
| G3 列式 K 线存储 | 把业务里现有的 `KLineDataBlock` 推广成通用存储,加推送节流 | 可行;但视口靠长度差猜"前插还是追加"这个问题,业务层修不了 |
| G4 指标入口 | 业务侧包一层强类型 helper,内部用 `ComputeInto`;实时 tick 下一律全量重算,不用 `IncrementalComputeFeature` | 可行 |
| G6 图层静默不画 | 约定:业务图层在 `OnProject` 里每帧都给本层发一个专属 Trait,保证被唤醒 | 可行,是约定不是保证 |
| G7 坐标 helper / 文字测量 | `IScale.Denormalize`(✅ 公开)写反向投影;`TextLayoutHelper`(✅ 公开)测量文字;填充先用 `DrawGeometry` 的 SVG 字符串 | 可行;SVG 填充数据一变就重新解析,性能有上限 |
| G8 范例 | 在业务仓库放一份经测试的模板屏幕 | 可行 |
| G9 `UseMemo` 内容版本 / 写提交语义 | 用 `UsePort` 的 `IsChanged` 自己维护一个计数器作为依赖;写多个端口一律用 `BeginTransaction` | 可行 |
| G10 分析器接入 | 在 hevo.drawing 根目录加 Directory.Build.props,统一接入分析器和生成器(这不算改框架) | 接入可行;分析器本身的漏报修不了 |
| G11 手势仲裁 | 业务在画布上挂 Preview(隧道)鼠标事件,画线或拖动时设 `Handled = true`;`ChartInteractionFeature` 用的是不带 handledEventsToo 的冒泡订阅,理论上收不到 | **未验证**,画线框架开工前先写个原型确认 |

**框架支持不了的功能,单独拉出来评估**:迁移会话不改框架,也不在业务层硬绕出一个脆弱的方案。遇到这种功能就停下,把它从迁移里拆出来,写一份评估,交给用户决定,其它功能照常迁移。评估要写清:

- 哪个功能、对应 FinNex 的哪部分代码;
- 框架为什么支持不了(具体到类和行号,最好附一个能复现的测试);
- 业务层能不能绕、怎么绕、代价和风险;
- 如果改框架,要改什么、影响哪些现有屏幕、工作量多大;
- 建议怎么做。

决定改框架的,单独开一个框架窗口去做,做完同步到 hevo.drawing、重新冻结,再回来迁移这个功能。B 表里标"未验证"的(比如 G11 手势仲裁),原型验证失败时也按这条处理。

目前已知要单独评估的有:**画线框架**(依赖 G11,手势仲裁未验证)和**麦语言公式引擎接入**(增量结果要和列式数据对齐)。

## 迁移适配:FuturesPC(FinNex)

### 迁移方式

目标是把 FinNex 的图表功能搬到本库(WPF)和业务仓库 hevo.drawing 里。FinNex 是 Avalonia 12 / .NET 8 应用,在这里只作为**功能规格**,不作为宿主。

- **UI 代码不能直接搬**:FinNex 用 Avalonia 的 `DrawingContext`、`Control`、指针事件、`DispatcherTimer`,接口程序集里也直接用了 Avalonia 类型。这些要按本库的 Feature / Layer / Trait 模型重写。
- **可以复用的是与 UI 无关的部分**:
  - 麦语言公式引擎:原生库 `libAnyCookerVMCore`,通过 P/Invoke 调用,与 UI 无关。
  - 纯计算类:叠加比例 `OverlayScaleCalculator`、跨夜盘的分时时间线 `TrendTimelineHelper`、九转等指标算法。
  - 画线工具的几何与命中算法。
  - 旧格式 XML 的读写:画线、偏好设置都要兼容老用户的数据。
- **数据模型要换**:FinNex 的 K 线是行式 record 列表,可以原地替换、`InsertRange(0)`;迁过来要改成列式摄入,遵守"历史写时复制、只有最后一根能原地改"的规则(见 G3)。

### 功能对照(摘要)

FinNex 一侧已逐项读代码盘点。

| 覆盖度 | 功能 |

| 已有 | K 线主图、分时图(期货夜盘要按品种配置时段)、历史分页、缩放 / 平移 / 视口、十字光标、时间轴 |

### 迁移中最大的两块新能力

1. **画线框架**:文档模型 `DataPort<DrawingDocument>`(不可变,每次修改发布一份新的,锚点用时间 + 价格);`DrawingInteractionFeature` 负责命中、拖动、吸附;工具渲染器做成注册表,不做封闭枚举;再加一个输入优先级机制 `IPointerClaim`,画线时暂停平移和缩放;持久化由宿主实现,需要兼容旧 XML。
2. **公式引擎**:FinNex 的引擎是原生库 `libAnyCookerVMCore`(麦语言),通过 P/Invoke 调用,增量输出是 FullReset / ReplaceLast / Append 这几种包,正好对应本篇数据切面第 2 条的 `DataChange`。建议**包装复用这个原生引擎**,而不是重写转译器;前提是先落地 G3 / G4 的变化描述协议。

### 建议迁移顺序

1. 单品种 K 线 + 历史分页 + 实时 tick 推送 + 十字光标 / 浮窗。用来验证 G2 / G3 / G5。
2. 分时图(含夜盘时段)+ 周期切换。用来验证切换入口和时段配置。
3. 成交量 / MACD 副图联动(等架构评审 P0-1 修完),加副图高度拖动。
4. 常用指标与参数切换;同时定下公式引擎的包装方案(依赖 G4)。
5. 最新价线 / 标签 / 倒计时、K 线标记、K 线样式变体。
6. 画线框架 MVP:趋势线、水平线、文字,加持久化和输入优先级。
7. 叠加品种、现货 / 基差、多日分时(等 P0-2);然后是主题、偏好分层、多图布局、AI 接入。

第 1–3 步做完,就能确认数据规则、切换、联动这三块的接口是否合适,再投入画线这类大工作量。
