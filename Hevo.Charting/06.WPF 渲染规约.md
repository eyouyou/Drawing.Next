# Hevo.Charting WPF 渲染规约

> 文档定位:Renderer 子系统在 **WPF 后端**下的运行时规约(`WpfDrawingRenderer`)。跨后端抽象层(`IRenderer<TBuffer, TContext>` / `IRendererProvider`)与"如何接入新 backend"见 [Renderer.md](Renderer.md)。
>
> 涵盖三块:
> - **§1–§8** 像素对齐契约 — `IDrawingSink` 的 WPF 实现 `WpfDrawingRenderer` 与调用方(业务 Layer / Feature)在像素对齐上的责任划分
> - **§14** 当前实现:snap + AA on 顶点对齐 + ChartCell 容器级配置
> - **§15** WPF 后端现状与性能优化路线图(批量 / 缓存 / 零 GC / 不实施项决策)

## 1. 背景与设计目标

### 1.1 渲染后端现状

仓库历史曾并行 `SkiaRenderer` + `WpfDrawingRenderer` 两个后端，命令协议两边语义不一致是早期像素对齐 bug 的主要来源。旧 `SkiaRenderer` 已于 commit `8350acf` 砍除。目前的上屏路径如下：

- **默认：WPF 矢量回放** —— [WpfDrawingRenderer](Renderers/DrawingRenderer.cs)（输出到 `DrawingContext`）。
- **位图回放** —— 图层设 `Mode = RenderMode.Bitmap` 时，框架把同一套绘制指令光栅化进 `WriteableBitmap`，图层 Visual 只挂这张位图。
- **可选上屏后端** —— `ChartCell.RenderBackend`（[IChartRenderBackend](Renderers/IChartRenderBackend.cs)）挂上后整 cell 的矢量画布改由后端上屏；Skia 实现在可选程序集 `Hevo.Charting.Skia`（`SkiaRenderBackend`）里，核心库不依赖它；该程序集是实验性的，不随产品打包，业务工程不引用。

本协议下文所有"渲染器内部"特指默认的 WPF 矢量后端。

光栅旁路 [WpfRasterRenderer](Renderers/WpfRasterRenderer.cs) 只 blit `WriteableBitmap`，不参与命令分发，不在本协议范畴。

### 1.2 历史责任错位（已修复，仅作动机记录）

旧协议把"是否对齐到像素"做成调用方的全局开关 `PushPixelSnapping(thickness)`，业务 Layer 同时还要手工 `halfT = t/2` 内缩"避免外围 Clip 切半"，两者叠加在 fill / stroke / 平滑曲线 混合场景下基本不可能正确，出帧普遍 2px 羽化。当前协议把所有像素算术下沉到渲染器内部，业务侧**零像素心智**。

## 2. 核心原则

### 原则 1：**默认锐利 + AA on 同时成立**

正交几何（grid / border / wick / 矩形边）的"物理 1px 锐利"由 `vertex snap` + `IsAntialias=true` 共同实现：snap 把 stroke 中心精确放到像素 .5（奇数线宽）或 .0（偶数线宽），AA scanline 在边界给出 100% / 0% 覆盖率，等价于纯 scanline 锐利。斜线段在同一路径下自动获得 AA 平滑边缘。

> 详见 §14：`vertex snap + IsAntialias=true` 是浏览器 / d3 / Chart.js 的业界默认做法，**不是**关 AA。

### 原则 2：**像素对齐对调用方完全透明**

业务 Layer 调用 `draw.DrawLine / DrawRectangle / DrawPolyline` 时传"原始（未偏移）坐标"。`+ 0.5f` / `halfT = t/2` / `MathF.Round` 这种像素算术**禁止出现在 `Hevo.Charting/Layers` 与业务工程程序集**，全部下沉到渲染器命令分发循环。

唯一例外是**宽度**:K 线实体 / 成交量柱这种"等宽柱"要取几个设备像素宽,由图层调 `ColumnWidth`(渲染器侧的 internal helper)决定,见 §4.6。位置仍然只交 scale 投影出的 DIP 坐标。

### 原则 3：**批量原语必须保留批量**

snap 在 `DrawRectangles` / `DrawLineSegments` / `DrawPolyline` 等批量 API 的**循环内部**逐顶点完成，**调用次数与原 batch 一致**。绝不为对齐拆调用、绝不退化成 N 次 `DrawRect`。

## 3. 数据模型

### 3.1 `HevoPen` 字段

```csharp
public record HevoPen(
    IHevoBrush Brush,
    double Thickness,
    double[]? DashArray = null,
    int LineCap = 0,
    int LineJoin = 0,
    bool IsAntialias = true   // 默认 AA on：1px H/V 由 snap 保证锐利、斜线段平滑
);
```

唯一与"像素呈现"相关的字段是 `IsAntialias`，默认 `true`。极少数"老电脑保护"场景下业务可显式传 `false` 走纯 scanline 锐利路径。

### 3.2 `LineStyle.Create` 仅控插值

```csharp
public static LineStyle Create(IHevoBrush brush, double thickness = 1.0, bool useSpline = false)
    => new LineStyle(new HevoPen(brush, thickness), useSpline);
```

`useSpline` **仅控制 `LineLayer` 是否走 Catmull-Rom 样条插值**，与 AA / 像素对齐完全无关。原协议中将该参数与"snap 与否"耦合的设计已废弃。

### 3.3 已删除的 API

| 旧 API | 状态 |
|--------|------|
| `IDrawingSink.PushPixelSnapping(thickness)` | 已删除（[DrawingExtensions.cs](Renderers/DrawingExtensions.cs)） |

## 4. 渲染器实现规约

### 4.1 共享 helper：`PixelSnap`

[Renderers/PixelSnap.cs](Renderers/PixelSnap.cs)，`internal`，业务侧不可见。

| 函数 | 语义 |
|------|------|
| `HalfPx(thickness)` | `Ceiling(thickness)` 为奇 → `0.5f`，否则 `0f`。**必须用 Ceiling 而非 (int) 截断**：否则 `thickness=0.5` 等亚像素线宽会被算成偶数（实测 grid 羽化的根因）。 |
| `Vertex(v, halfPx)` | `floor(v + 0.5 − halfPx) + halfPx`:宽 n 的线 = 几何矩形 [v − n/2, v + n/2],两边四舍五入到像素边界后的中点。奇数线宽 = `floor(v) + 0.5`,偶数线宽 = `floor(v + 0.5)`。 |
| `SnapEndpoints(p1, p2, halfPx, out a, out b)` | **单线段端点 snap，非对称**：H 时平行轴(线方向)端点四舍五入到像素边界 + 垂直轴按 `Vertex`；V 对偶；斜线段两轴都 `Vertex`。详见 §14.2 — 对称 .5 snap 会让端点列只 50% 覆盖、淡色 grid 看不见。 |
| `FillRect(rect, k)` | 填充矩形 / 裁剪框四边四舍五入到设备像素边界 `floor(v·k + 0.5) / k`。 |
| `InsideStroke(rect, thickness)` | 先把外边界 4 个角四舍五入到整像素，再 inside-shrink halfT。**取整必须先于 shrink**：layout 的浮点 plotArea 直接 +halfT 会让 stroke 中心落浮点位置 → AA 横跨 2px 羽化。 |

**唯一的覆盖规则**:横平竖直的边(线的两侧、线端、矩形四边、裁剪框)一律四舍五入到最近的像素边界 `floor(v + 0.5)`,恰好压在像素中心上的平局归右 / 下。位图后端的光栅核心(`PixelMath.EdgePixel`)是同一条规则,所以两个后端横竖内容逐像素一致。

为什么线和矩形必须同一条规则:以前竖线按 `round(x)` 落列、填充矩形按 `ceil(v − 0.5)` 取边,奇数宽时两者差半格——同一个中心上的 1px 影线 / 十字线和奇数宽 K 线实体,有一半小数位置会错开一列,实体宽度也随小数位置在 n / n+1 间跳。平局归右 / 下是因为 100% 下整数坐标上的 1px 线(鼠标位置、布局边界)最常见,这样它们落在 [x, x+1) 这一列,跟历史行为一致。不做成配置项:这是渲染器内部细节。

### 4.2 命令分发模板

每个 stroke 类原语都按"取 pen → 算 halfPx → snap 顶点 → 调 dc"展开。模板见 [DrawingRenderer.cs](Renderers/DrawingRenderer.cs)，关键分支：

| 命令 | 分发逻辑 |
|------|---------|
| `DrawLine` | `HalfPx + SnapEndpoints + dc.DrawLine` |
| `DrawLineSegments` | 配对循环内 `SnapEndpoints` 后 `BeginFigure/LineTo` 写入复用 `StreamGeometry`，最终 `dc.DrawGeometry` 一次出 |
| `DrawPolyline` | `HalfPx` + 循环逐顶点 `Vertex(x, h) / Vertex(y, h)` 写入 `StreamGeometry`，`dc.DrawGeometry` 一次出 |
| `DrawRectangle` | fill 走原 rect；stroke 走 `InsideStroke + dc.DrawRectangle(null, pen, sr)` |
| `DrawRectangles` | 循环内逐 rect：fill 原 rect，stroke 走 `InsideStroke`（**不能用 StreamGeometry 多 figure 批量**：WPF 在 figure 间留下幻线，K 线 body 之间会冒红色"趋势线"伪影） |
| `DrawRoundedRectangle` | `InsideStroke + dc.DrawRoundedRectangle`，圆角部分由 AA on 的 stroke 自然平滑 |
| `DrawEllipse` | 圆心 `MathF.Round` + 直接 `dc.DrawEllipse`（dot 直径 ≥ 3 时 .5 偏移视觉不可分辨） |
| `DrawPolygon` | 填充:顶点 `FillVertex`(设备像素边界,同 `FillRect`)写进非零环绕的 `StreamGeometry`;描边:顶点 `Vertex`(同 polyline)另建一个闭合几何。见 §4.7 |
| `DrawBand` | `FillGeometry.Band` 拆成闭合图形(NaN 断开、按上下穿越分段),每种颜色一个多 figure 填充几何,顶点 `FillVertex`;描边只描上下两条边,顶点 `Vertex`。见 §4.7 |

### 4.3 WPF 端的 AA 控制

`HevoPen.IsAntialias` 字段默认 `true`，**WPF `Pen` 类型本身不支持 paint 级 AA 开关**。WPF 端**全图抗锯齿**（ChartCell 不设 `EdgeMode.Aliased`），`pen.IsAntialias=false` 在 WPF 路径下被忽略。

实际效果：横竖线 / 矩形 / 裁剪框由渲染器按**设备像素**对齐（顶点 snap + 整数 DIP 线宽取整到整数设备像素，规则同 Skia 后端），抗锯齿下也是实心像素，100% / 125% / 150% DPI 都锐利；斜线 / 曲线平滑。这跟 ECharts（zrender `subPixelOptimize`）、Highcharts（`crisp`）的做法一致。

### 4.4 性能注意

- `HalfPx(thickness)` 应在循环外预算一次（`DrawPolyline` / `DrawRectangles` 内已遵守）
- `Vertex(...)` / `SnapEndpoints(...)` 单点开销 < 1ns、无 allocation
- WPF `StreamGeometry.Open()` 单次构造目前每帧 new；`StreamGeometry` 复用是路线图项（§15）

- **必须**遵守 stroke 顶点 snap + `IsAntialias` 透传契约

新 renderer 都应通过 §6 的视觉黄金路径。

### 4.6 等宽柱(K 线实体、成交量柱)

位置和宽度都只从 scale 来([CoordinateExtensions](Core/CartesianCoordinate.cs)):

- 中心 `ProjectDomainToScreen(area, range, axis, i)` = `Normalize(i)` 铺到绘图区。K 线、成交量柱、十字线(ChartInteractionFeature)共用,同一个索引上的它们天然同列。
- 一格宽 `ProjectDomainSlotWidth(area, range, axis, i)` = `Normalize(i + 0.5) − Normalize(i − 0.5)` 铺到绘图区。图层逐根取,自定义不等间距的 scale 只要 `Normalize` 写对,图层不用改。

宽度取整数设备像素([Renderers/ColumnWidth.cs](Renderers/ColumnWidth.cs)):整数宽在上面的覆盖规则下每根都一样宽,中心相同、奇偶相同的竖线落在正中。

- `ColumnWidth.Of(一格宽, 比例, k, 中线像素)`:在 [理想 − 1, 理想 + 1] 内取跟中线同奇偶、离理想值最近的整数,理想 = 一格 × 比例 × k。比例 < 1 时不超过 floor(一格 × k) − 1,有 padding 就一定看得见空隙(格子太小时空隙优先于奇偶)。
- CandleLayer:比例 = 1 − BodyPadding,中线 = 影线线宽换算的设备像素;十字星最小高度 `ColumnWidth.MinHeight(k)`(1 DIP 按线宽规则换算,125% / 150% 下都是 1px)。
- BarLayer:比例 = WidthRatio,没有中线时按 1px 取奇偶,跟默认 1px 影线 / 十字线同轴。
- 奇偶对不上时(2px 影线配奇数宽成交量柱、格子太小)偏半像素,方向随小数位置。

验收:`CandleColumnPixelTests`(离屏截图量实体宽 / 影线偏移 / 间隙 / 成交量中心 / 十字星高,含不等间距 scale)、`ColumnWidthTests`(线与矩形同规则、宽度规则)。设环境变量 `HEVO_SHOT_DIR` 跑 `CandleColumnShotTool` 可导出对比截图与统计。

### 4.7 填充:`DrawPolygon` / `DrawBand`

任意形状的填充走这两条指令,不要再拼 SVG 字符串调 `DrawGeometry`:SVG 按字符串缓存,数据一变(画线工具被拖动、填色跟着 K 线滚动)每帧都是一次新的解析 + 新的缓存项。

| 指令 | 用途 | 数据 |
|---|---|---|
| `DrawPolygon(brush, pen, List<HevoPoint>)` | 实心箭头 / 三角标记、矩形 / 平行四边形 / 斐波那契区域等画线工具 | 顶点列表,首尾自动闭合;NaN / ∞ 顶点跳过,有效顶点不足 3 个不画 |
| `DrawBand(brush, pen, HevoBand, crossedBrush = null)` | 区间填色、布林带 / 通道填充、云图、阈值上下分色 | `HevoBand.Upper` / `Lower` 按下标对齐;任一边 NaN 的样本断开带子 |

- **数据不拷贝**:两条指令都只引用列表 / `HevoBand`,跟 `DrawPolyline` 一样做成图层的跨帧字段,每帧 `Clear` 后重填(0-GC);同一个 `HevoBand` 一帧只录一次。
- **断带**:`HevoBand.AddGap()` 或直接写 NaN。不要像折线那样跳过 NaN —— 跳过会把缺口两侧连成一片。
- **分段两色**:给了 `crossedBrush` 时,上边在上(屏幕 y 更小)的部分用 `brush`,穿越后的部分用 `crossedBrush`,穿越点在相邻样本之间线性插值;阈值分色把 `Lower` 全填阈值线的 y。不给就整条一个颜色。
- **描边**:`DrawPolygon` 描整圈;`DrawBand` 只描上下两条边(两端竖边不描),中轨等其它线照常 `DrawPolyline`。
- **像素**:填充顶点取到设备像素边界(`PixelSnap.FillVertex`,即 `FillRect` 那条 `floor(v·k + 0.5) / k`),横竖边跟 `DrawRectangle` 逐像素一致、任意 DPI 都没有半透明边;斜边顶点最多挪半个设备像素,由抗锯齿画平滑。描边顶点同 polyline 的 `Vertex`,线宽按 `DeviceThickness`。填充一律**非零环绕**(`StreamGeometry` 默认奇偶,渲染器显式设成非零,跟位图 / Skia 后端一致)。
- **拆分只有一份**:哪些点连成哪个图形、NaN 在哪断、穿越点算在哪,由 `Renderers/FillGeometry.cs` 统一做,三个后端只负责把点写进各自的几何(WPF `StreamGeometry` / 位图扫描线边表 / `SKPath`)。
- **多 figure**:带子的各段放在同一个填充几何里(每种颜色一个)。`DrawRectangles` 当年的"figure 间幻线"在这里没有复现:`FillDrawingTests` 截图检查断带处整片为空。

范例:[DocSamples/Fill/RangeShadeLayer.cs](../Hevo.Charting.Tests/DocSamples/Fill/RangeShadeLayer.cs)(价格相对阈值的区间填色,带暖机期 / 缺口断带)。验收:`FillDrawingTests`(录制、拆分、跟填充矩形 / 位图后端逐像素一致、125% / 150% 无半透明边、分段两色、位图后端 0 分配)、`DocSampleTests.RangeShadeLayer_*`。

文字测量(`MeasureText`)还没有:量字要用渲染器手里的 `FormattedText` / 字形缓存,图层录制时拿不到,而且三个后端的宽度口径要先统一,不是 `TextLayoutHelper` 上加一层能解决的。

## 5. 业务图层契约

### 5.1 调用方规则

- ✅ 直接调用 `draw.DrawLine / DrawRectangle / DrawPolyline`，传原始（未偏移）坐标
- ✅ 创建 pen 用 `LineStyle.Create(brush, thickness)`；需要 spline 插值再传 `useSpline: true`
- ❌ 不要写 `+ 0.5` / `halfT` / `MathF.Round` 像素偏移
- ❌ 不要 `using PushPixelSnapping`（API 已删除）
- ❌ 不要在层级局部 `dc.PushTransform(translate(.5))` 模拟对齐

发现某种几何在锐利模式下渲染不正确 → **修渲染器**，不要在 Layer 里打补丁。

### 5.2 Series 折线 / 平滑曲线

```csharp
LineStyle.Create(Colors.Red, 2, useSpline: true);   // 折线走 Catmull-Rom 插值
LineStyle.Create(Colors.LightGray, 1);              // grid / border 直线段
```

`useSpline` 仅控制 `LineLayer` 的几何插值（直线段 vs 样条曲线），**与像素对齐 / AA 都无关**。AA 由 `HevoPen.IsAntialias` 决定，默认 `true`。

### 5.3 已知合规图层

业务侧已经无 `PushPixelSnapping` / `halfT` 残留（commit `b60f57e fix 像素对齐` 清理完）：[PlotAreaDecorLayer](Layers/PlotAreaDecorLayer.cs)、[GridLineLayer](Layers/GridLineLayer.cs)、[CandleLayer](Layers/CandleLayer.cs)、[BarLayer](Layers/BarLayer.cs)、[LineLayer](Layers/LineLayer.cs) 都直接传未偏移坐标。

## 8. FAQ

**Q：为什么不在 `IDrawingSink` 加 `DrawCrispLine` / `DrawCrispRect` 这种显式版本？**
A：会让"对不对齐"成为调用方的选择，但对齐本身在图表里就是默认正确性。"显式版本"等于把每个调用点都变成可能写错的地方。Pen 携带语义 + 渲染器内部 snap 是 "Pit of Success" 设计。

**Q：批量 API（如 `DrawRectangles`）会因为 snap 退化吗？**
A：不会。snap 算术在批量循环的内部、紧贴 `dc.DrawRectangle` 之前完成，循环次数 = 原批量大小。每个 vertex 多一次 `MathF.Floor + 加常量`，纳秒级、零分配。

**Q：偶数线宽（如 2px）也走 snap 吗？**
A：走。`HalfPx(2) == 0`，`Vertex` 等价于 `floor(v + 0.5)`，把可能的浮点误差取整到像素边界，对 2px stroke 同样必要。

**Q：透明 / 半透明描边呢？**
A：snap 只动顶点位置，不动颜色 / alpha。半透明描边在锐利路径下边界依然锐利、内部仍是声明的透明度。

**Q：`useSpline: true` 后 series 还需要做点什么吗？**
A：不需要。AA 默认 on，`useSpline` 单纯控制 `LineLayer` 用 Catmull-Rom 还是直线段。两个维度独立。

**Q：WPF 端如何关 AA？**
A：不关。`HevoPen.IsAntialias=false` 在 WPF Pen 上无效（API 限制），WPF 端全图抗锯齿，横竖内容靠设备像素对齐保持锐利（§4.3）。

## 14. 最终方案：snap + AA on（2026-04-30）

### 14.1 设计依据

`vertex snap + IsAntialias=true` 是浏览器 / d3 / Chart.js / SkiaSharp 官方示例画 1px 锐利线的**业界默认做法**。早期一度怀疑 "stroke 算法本身有 ±1 像素抖动" 而尝试 fill rect 替换 stroke 路径，实测下来标准做法已经能给出精确 1px——AA scanline 在 snap 后的 .5 中心两侧各 50% 覆盖,合并到唯一一列像素 100% 覆盖,就是教科书锐利线。

→ **本协议不再走 fill rect 替换 stroke 路径**,所有 stroke 一律 snap + AA on。

### 14.2 H/V 单线的非对称 snap（关键细节）

⚠️ **H/V 直线不能两轴都 .5 snap**，否则在 AA on 路径下端点会羽化。

设 1px 水平线 `(0, 10) → (600, 10)`，对称 .5 snap 后：
- 端点 = `(0.5, 10.5)` 和 `(600.5, 10.5)`
- Skia stroke 几何 X∈`[0.5, 600.5]`，AA scanline 计算各列覆盖率：
  - 列 X=0：50% 覆盖（淡色 grid 在低对比背景下几乎不可见）
  - 列 X=1..599：100% 覆盖
  - 列 X=600：50% 覆盖（plotArea clip 切掉）
- **视觉效果：grid 线左端淡得看不见、右端被 clip 切掉**

正确做法是 H/V 走**非对称 snap**：
- 平行轴（线方向）：端点四舍五入到像素边界 → 端点列像素 100% 覆盖
- 垂直轴（线宽方向）：`Vertex` → 奇数线宽中心落像素中心、偶数落像素边界

斜线段两轴都 .5 snap（标准 vertex snap）。`PixelSnap.SnapEndpoints(p1, p2, halfPx, out a, out b)` 封装这个判定：

```csharp
// End(v) = floor(v + 0.5):线端同填充矩形的边
// 水平
if (p1.Y == p2.Y)
{
    float y = Vertex(p1.Y, halfPx);
    a = new HevoPoint(End(p1.X), y);     // 平行轴取整到像素边界
    b = new HevoPoint(End(p2.X), y);
}
// 垂直
else if (p1.X == p2.X)
{
    float x = Vertex(p1.X, halfPx);
    a = new HevoPoint(x, End(p1.Y));
    b = new HevoPoint(x, End(p2.Y));
}
// 斜线段
else
{
    a = new HevoPoint(Vertex(p1.X, halfPx), Vertex(p1.Y, halfPx));
    b = new HevoPoint(Vertex(p2.X, halfPx), Vertex(p2.Y, halfPx));
}
```

`DrawLine` / `DrawLineSegments` 用 `SnapEndpoints` 替代旧的对称 snap；`DrawPolyline` 中各段虽然也独立但首尾相连成一条 path，端点羽化不可见，仍走对称 snap 即可。

`DrawRectangle` / `DrawRectangles` 走 `InsideStroke` + Skia rect stroke：rect outline 是闭合 4 边几何，相邻边的 stroke 在角点 miter join 互补，每个边界像素都能拿到 100% 覆盖，无端点羽化。

### 14.3 标准做法的工作原理

`vertex snap + IsAntialias=true` 的输出：

| 输入 | snap 后的中心 | AA scanline 算法 | 输出像素 |
|------|--------------|----------------|---------|
| 1px 水平线 Y=10.3 | Y=10.5 | Y=10 像素覆盖率 100%；Y=9 / Y=11 覆盖率 0% | **精确 1 像素行**，纯色 |
| 2px 水平线 Y=10.3 | Y=10.0 | Y=9 / Y=10 像素各 100% 覆盖 | **精确 2 像素行**，纯色 |
| 斜线段（45° 1px 粗） | snap 顶点到 .5 | 每个像素按几何覆盖率算 alpha | **平滑 AA 边缘** |
| 1px 垂直线 X=15.7 | X=15.5 | X=15 像素覆盖率 100% | **精确 1 像素列**，纯色 |

H/V 线在 snap 后中心精确落在 .5（奇数线宽）或 .0（偶数线宽），AA scanline 在边界恰好命中整数像素 → coverage 100% / 0% → 视觉上等价于"无 AA 的锐利线"。**斜线段同时享受 AA 平滑**——一条路径同时正确处理两类几何。

### 14.5 业务侧契约（不变）

```csharp
LineStyle.Create(Colors.Red, 2);   // 默认 IsAntialias=true，业务零关心
LineStyle.Create(Colors.Red, 2, useSpline: true);   // 平滑曲线
new HevoPen(brush, 1, IsAntialias: false)  // 极少需要：强制纯 scanline 锐利
```

`HevoPen.IsAntialias` 默认 true 保证开箱即得正确视觉；业务侧若有"老电脑保护"等特殊需求可显式 false 走 nearest-pixel scanline。

### 14.6 跨后端

- **Skia (Hardware)**：`paint.IsAntialias = pen.IsAntialias`，per-pen AA 完全生效
- **WPF (Software)**：WPF Pen 不支持 paint 级 AA 开关，全图抗锯齿 + 设备像素对齐；`pen.IsAntialias` 在 WPF 路径下被忽略

### 14.7 关键不变量

1. **每条 stroke 顶点都过 snap**：保证 1px 在 .5、2px 在 .0
2. **AA on 是默认**：`HevoPen.IsAntialias = true`
3. **fill 路径 AA off**：`GetFillPaint` 仍 `IsAntialias = false`（多边形 / 矩形 fill 在 AA off 下边界严格落在像素，避免边缘羽化）
4. **DashArray 自动正确**：所有 stroke 走原生 stroke 路径，`SKPathEffect.CreateDash` / WPF `DashStyle` 自然生效

### 14.8 给后续维护者的话

- 如果再遇到 1px stroke "羽化" 现象：**第一步检查 `pen.IsAntialias` 是否 true**（默认）、第二步检查上游坐标是否被某个 layer 提前 round 成整数（破坏了 snap 的 .5 对齐）
- 不要再退回 fill rect 替换 stroke 的方案——会让 DashArray、stroke cap / join 等 pen 配置全部失效

### 14.9 ChartCell 容器级配置(父布局亚像素免疫)

ChartCell 对外承诺:业务侧 `new ChartCell { Template = schema }` 后挂任何容器(`UniformGrid` / `Grid *` / `WrapPanel` / 自定义 Panel),无需关心父级 `UseLayoutRounding` / `SnapsToDevicePixels` / 像素对齐。父布局给的位置即使是 X=374.25,cell 内部像素仍按原栅格呈现。

[ChartCell.cs](Core/ChartCell.cs) 内部防线:

```csharp
UseLayoutRounding = true;     // 自身 measure/arrange 落整像素
SnapsToDevicePixels = true;   // 子元素边缘 snap
// 不设 EdgeMode.Aliased:全图抗锯齿,横竖内容由渲染器按设备像素对齐(§4.3)
```

锐利靠渲染器的设备像素对齐,不靠 `EdgeMode.Aliased`:横竖线 / 矩形在任意 DPI 都是实心像素,斜线 / 曲线平滑(跟 ECharts / Highcharts 一致)。

**原点对齐**:渲染器在图层局部坐标里取整,前提是图层原点落在设备像素上。`UseLayoutRounding` 只取整 cell 相对父元素那一段,祖先在小数位置(`Grid *`、GridSplitter、`Canvas.Left=20.4`、125% DPI 下的整数 DIP)时原点仍在像素中间,不处理的话交互层和关缓存的静态层整体发虚(实测 4051 个非纯色像素),开缓存时只有静态层被 BitmapCache 贴回整像素,两边不一致。

- 矢量图层:挂上画布时(`ChartDrawingCanvas.InsertVisual`)设 `XSnappingGuidelines` / `YSnappingGuidelines = {0}`,对齐归宿主、图层不用管;由合成器把原点贴到最近的设备像素。只作用于渲染,不改布局、命中测试、鼠标坐标;父布局变化、拖动、祖先 `RenderTransform` 动画中都跟着(真实屏幕 100% / 125% / 150% 实测都是 0 个非纯色像素;去掉 guideline 时 125% 关 / 开缓存 5120 / 952,150% 为 6179 / 1136)。画面相对布局位置最多挪半个设备像素。
- 位图图层(`RenderMode.Bitmap`):guideline 只挪几何不挪 `DrawImage`,`ChartCell` 在 `LayoutUpdated` / DPI 变化 / 每次画位图图层前算出原点到最近设备像素的偏移,`BitmapLayerSurface.Mount` 把位图包在这个平移里(静态层开缓存时为 0,缓存自己贴整像素)。祖先 `RenderTransform` 动画不触发布局,动画停在小数位置后位图图层下一次重画就对齐;局限:动画进行中位图图层不重画就跟不上(要跟就得常驻 `CompositionTarget.Rendering`,违背静置不占 GPU)。
- Widget 层(`InteractionCanvas` 里的 WPF 控件):靠 WPF 自己的 `SnapsToDevicePixels`,实测(100%:偏移 0 / 20.4 / 20.6;125% / 150%:偏移 20.4 / 21)Border 边框与交互层竖线落在同一列、没有半透明像素,不用另做处理。
- Skia 后端宿主:未覆盖,见 TODO.md "Skia 后端宿主的原点对齐"。
- 不采用:给画布加反向 `RenderTransform`(会改鼠标坐标,且动画中跟不上);画布(UIElement)上的 snapping guideline(实测无效);给位图图层挂 `BitmapCache`(合成器给缓存取整跟 guideline 不一样,偏移 20.6 / 7.5 时与矢量图层差 1 个设备像素);要求业务在根 Window 设 `UseLayoutRounding`(把 cell 的正确性外包给容器)。

**BitmapCache**:`_drawingCanvas` 挂上 `BitmapCache`(`StaticCachePolicy`,默认 On)后,缓存按抗锯齿栅格化 —— 全图本来就是抗锯齿、横竖内容已按设备像素对齐,所以开不开缓存画面逐像素一致,切换缓存也不用重录图层。(以前全图走 `EdgeMode.Aliased` 时,缓存会让 Aliased 失效、小数坐标的 K 线实体两侧发虚;改成全图抗锯齿后这个问题不存在了。)回归测试 `StaticCacheAliasingTests`:挂进窗口截图开 / 关缓存一致;100% / 125% / 150% DPI 下横竖线、小数坐标实体、矩形描边、裁剪框没有半透明像素;斜线有抗锯齿边缘;祖先小数偏移下(矢量 / 位图 × 开 / 关缓存、125% / 150%、父布局变化后)静态层和交互层没有半透明像素,鼠标换算落在画出来的那列像素上。

### 15.2 不实施项 — 决策记录

> ① 命令分发 batch detector 与 ④ DevTools KPI overlay 已落地（见 §15.1 表）。② / ③ / ⑤ 三项均判定"不实施"，理由见下文。后续若业务自建诊断层跑出新瓶颈,再开新条目而非回退到这三项。

#### ② StreamGeometry pool（不实施）

**现状**：[DrawingRenderer.cs](Renderers/DrawingRenderer.cs) 的 `BuildPolyline` / `BuildLineSegments` / `BuildRectangles` / `BuildLineBatch` 每次都 `new StreamGeometry()` + `Freeze()`。每帧 5–10 个一次性 Geometry。

**为什么不实施**：

1. **`StreamGeometry` 就是 WPF 设计来一次性 Freeze 的工具**（`SealedFreezable`），内部状态比 `PathGeometry` 紧凑——这是正确选择。
2. **替代方案 `PathGeometry` + `PolyLineSegment` 池反向更慢**：`PolyLineSegment.Points` 是 `PointCollection`（Freezable 子类），每次 `Add` 走 freezable 通知 + change tracking，单点开销显著高于 `StreamGeometryContext.LineTo`。
3. **不在前 3 大 GC 源**：每帧 5–10 个 Geometry 不是热点，业务自建诊断层量化前不应优化。
4. **真有 alloc 压力时正确方向是复用 `StreamGeometryContext`** 或预生成共享几何，**不是**换底层几何类型。

**结论**：保留 `new StreamGeometry()` + `Freeze()` 的现状。若未来业务自建诊断层跑出"Geometry alloc 进入前 3 大 GC 源"再重新评估,且方向应是 context 复用而非 PathGeometry 池。

#### ③ Per-Op AA 切换（不实施）

**问题**：当前 [DrawingRenderer.cs:336-359](Renderers/DrawingRenderer.cs:336) 的 `GetPen` 不读 `desc.IsAntialias`，因为 WPF `Pen` 不支持 paint 级 AA 开关。`HevoPen.IsAntialias=false` 在 WPF 路径下被忽略——这是 [Style.cs:136](Renderers/Style.cs:136) 注释明确承认的。

**方案探索**：要让 per-op AA 真生效，必须改 ChartCell 架构 — 每个不同 `EdgeMode` 的命令子流走独立 `DrawingVisual`，render 时按 EdgeMode 分桶。代价：`DrawingVisual` 数量翻倍、composition tree 复杂、跨 visual 的 z-order 管理变难。

**结论**：**不实施**。当前全图抗锯齿 + 设备像素对齐（§4.3 / §14）已覆盖所有场景。`HevoPen.IsAntialias` 字段保留作"未来引入新后端时的契约位"，WPF 端永久忽略并在 `Style.cs` 注释明确这一点。

（早先全图走 `EdgeMode.Aliased` 时折线斜线段锯齿明显，这里曾记录过 layer 级切回抗锯齿的方案；改成全图抗锯齿后不再需要。）

#### ⑤ Per-Layer raster cache（不实施 — 方针下放业务）

**为什么不做框架级机制**：

1. **现状已有粗粒度方案**：[ChartCell.cs:215](Core/ChartCell.cs:215) `BitmapCache` 挂在 `_drawingCanvas` 上，`StaticCachePolicy` 默认 On，相当于"per-cell raster cache"。多 cell 场景下系统已隐式做了 per-static-tree raster。
2. **AxisLabel 真实瓶颈不在 layer 重画**：贵在 `FormattedText` 构造，已被 [DrawingRenderer.cs:40](Renderers/DrawingRenderer.cs:40) `LruCache<FormattedTextKey, FormattedText>(4096)` 拦下。再上 `RenderTargetBitmap` 缓存的是已缓存对象的 composite 调用，几乎免费。
3. **`RenderTargetBitmap.Render` 不便宜**：软件渲染管线，每次 invalidate 全量 re-render，命中率 < 70% 净亏。靠业务自建诊断层监控命中率反向证明哪些 layer 不该开 — 一开始就别开。
4. **5–7 天工作量 + LRU 池 + 字节预算 + DPI 重建 + 与现有 `BitmapCache` 共存路径**，系统复杂度跃升一档，换的是少数候选 layer 也许快几 ms。
5. **内存陷阱无法绕开**：朴素方案多 cell 场景下 0.5 GB 起步;修订版的 64 MB 池 + LRU + 自动降级本质是放弃信号。

**方针**：业务侧若有"贵 × 静 × 小"的 layer（典型如 Watermark / Logo）出现卡顿，自行在该 layer 的子 `DrawingVisual` 上挂 `CacheMode = new BitmapCache(...)`，5 行代码即可。WPF 原生就支持子 visual 级 BitmapCache，框架不提供 per-layer 缓存机制,也不引入 `RenderMode` 枚举或 `LayerCacheKey` 抽象。
